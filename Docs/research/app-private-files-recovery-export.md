# App-private Android files and recovery-package export

Investigated 2026-10-07 for [Research app-private Android files and cloud recovery-package export](https://github.com/A3R0-01/Cloud-Epub/issues/11), supporting [Decide account privacy, recovery, and six-month expiration](https://github.com/A3R0-01/Cloud-Epub/issues/5). This is documentation research, not implementation or a cryptographic decision. Statements marked **Implication** are engineering conclusions from the cited platform facts.

## Findings that unblock the product discussion

Android supports keeping downloaded books unavailable to ordinary file explorers while the app reads them offline. Use the internal application sandbox and preserve the distinction between local library unlock and cloud session validity. This cannot promise protection from a compromised device or retract copies already possessed. A readable recovery-package export is intentionally outside that private-library boundary.

Two export mechanisms have different guarantees: Android's system Save As picker reaches participating providers and user-selected destinations; a dedicated Google Drive adapter can create the requested `Cloud ePub/Recovery` hierarchy. Neither mechanism makes an exported secret uncopyable. Folder names are mutable and non-unique; path correctness needs folder IDs, not string concatenation. Details and source evidence follow.

## Private books, temporary files, and offline access

- Android internal `filesDir` and `cacheDir` prevent other apps from accessing their files; no storage permission is needed. Internal locations are OS-encrypted on Android 10 and later. External app directories have different historical protections and are not the appropriate cross-version basis for sensitive books. Internal files are removed on uninstall. **Implication:** ordinary file explorers should see no readable app-managed EPUB in Downloads, shared documents, media storage, or external app folders. Renaming files or adding `.nomedia` does not establish the required boundary. [Android app-specific files](https://developer.android.com/training/data-storage/app-specific)
- The sandbox is enforced through app UIDs and kernel-level isolation. AOSP explicitly warns that its protections are not invulnerable. **Implication:** describe the promise as ordinary explorer exclusion on a supported, uncompromised device; do not guarantee it against root, privileged debugging, or an attacker controlling the app/OS. [AOSP Application Sandbox](https://source.android.com/docs/security/app-sandbox)
- App-private storage can be deliberately shared through `FileProvider` URI grants. **Implication:** library content must not be exposed by exported document providers, broad FileProvider paths, external-reader intents, or share/open-with actions. This needs an inventory of actual app components and the eventual renderer. [Android app-specific files](https://developer.android.com/training/data-storage/app-specific)
- EPUB is a container of publication resources packaged using ZIP. **Implication:** auditing only the downloaded `.epub` misses extracted chapters, images, fonts, thumbnails, search indexes, databases, and renderer/WebView caches. The selected renderer must support private resource access; prefer decrypting resources as needed over writing a second persistent plaintext EPUB. Renderer compatibility and memory/storage cost remain untested. [W3C EPUB 3.3, OCF ZIP container](https://www.w3.org/TR/epub-33/#sec-zip-container)
- Sensitive temporary data belongs in internal cache, which Android may delete under storage pressure; the app must manage cleanup itself. **Implication:** renderer temporary files need bounded lifetimes and cleanup on close, lock, logout, restart after a crash, and failed import. Persistent offline downloads need persistent private storage, not cache. Deleting temporary files is not a forensic secure-erasure guarantee. [Android app-specific files](https://developer.android.com/training/data-storage/app-specific)

## Encryption and local authentication boundaries

Android Keystore supports non-exportable keys and authentication requirements using device credentials/strong biometrics. Hardware support and enforcement vary and are inspectable. The official documentation says a compromised process or OS may still use keys on the device even when key extraction is prevented. **Implication:** a biometric dialog alone is not proof of cryptographic enforcement; the separate security design must connect local authentication to usable decryption authority and define authentication duration, screen-lock removal, key invalidation, and recovery paths. OS encryption also does not select the app's cloud/library encryption protocol. [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

Jetpack `EncryptedFile` is deprecated in security-crypto 1.1.0; its documentation also warns that encrypted files and generated keyset preferences require backup exclusions. Its replacement advice to use `java.io.File` does not mean `File` performs encryption. Do not base a new cryptographic design on an old convenience API without reviewing supported primitives and key management. [EncryptedFile reference](https://developer.android.com/reference/androidx/security/crypto/EncryptedFile)

**Implication:** cloud expiration, cloud session revocation, local lock, and explicit logout are separate transitions. An offline device cannot immediately learn a remote revocation. Keeping downloaded books usable after cloud expiration requires retaining usable local decryption authority, whereas a logout policy that destroys all local keys may prevent that. The product discussion must define explicit logout; this research selects neither retention nor deletion behavior. It does not infer view-once deletion or DRM.

`FLAG_SECURE` can block screenshots and non-secure display/casting, but Android documents reliability limitations, particularly on older devices. **Implication:** screenshot restrictions require a separate product choice and are not entailed by file-explorer exclusion. No window flag prevents another camera photographing a displayed page. App-private copies cannot remove an original EPUB already stored in another provider/device location. [Android secure sensitive activities](https://developer.android.com/security/fraud-prevention/activities)

## Backup and device transfer

Auto Backup includes internal files, preferences, and databases by default. Cache and no-backup directories are excluded. `android:allowBackup="false"` alone does not disable every manufacturer's device-to-device transfer on Android 12 and later. Use applicable legacy `fullBackupContent` rules and modern `dataExtractionRules`; modern cloud-backup and device-transfer sections are independent, and an omitted mode normally enables that mode. Current documentation additionally describes cross-platform-transfer rules. **Implication:** exclusions must cover library resources, metadata/indexes, cloud/provider credentials, local key wrappers/keysets, and every applicable transfer mode. Audit third-party SDK storage too. A device replacement should authenticate and download again rather than inherit these secrets. [Android Auto Backup](https://developer.android.com/identity/data/autobackup)

The optional user-requested recovery text export is a distinct action, not automatic Android app backup. Once exported, it follows the chosen provider's own storage, sync, sharing, and retention behavior.

## Export to a chosen provider through Android

The Storage Access Framework (SAF) exposes local/cloud services implementing a `DocumentsProvider`; it cannot reach every imaginable provider without one. [Android SAF overview](https://developer.android.com/guide/topics/providers/document-provider)

`ACTION_CREATE_DOCUMENT`, MIME type `text/plain`, and a suggested filename open the system Save As flow. The user chooses the destination. No broad storage permission is required. `EXTRA_INITIAL_URI` supplies an initial location, not a forced folder path. Create-document cannot overwrite: the system appends a numbered suffix when names collide. Folder-tree access is an alternative where the provider supports it, but does not provide a universal Drive hierarchy guarantee. **Implication:** SAF supports “save to your chosen location,” not an automatic exact `Cloud ePub/Recovery` path. [Android documents and files](https://developer.android.com/training/data-storage/shared/documents-files)

**Implication:** picker cancellation means no successful save. After choosing a URI, write failures can leave an empty/partial document; cleanup is best effort because provider deletion/write capabilities differ. Closing a provider stream establishes a local provider write, not universal proof that a remote upload completed. Offline behavior is provider-dependent: present failure or pending state honestly and do not count it as confirmed cloud recovery storage. The document/root APIs expose variable capabilities, including write/delete support and offline limitations. [Document capabilities](https://developer.android.com/reference/android/provider/DocumentsContract.Document), [Root capabilities](https://developer.android.com/reference/android/provider/DocumentsContract.Root)

## Exact Google Drive hierarchy and client-only authorization

Drive API v3 creates folders using `application/vnd.google-apps.folder` and places children by parent IDs. **Implication:** a dedicated adapter can create `Cloud ePub` in My Drive, then `Recovery` beneath that folder, then the text package beneath Recovery, and retain/verify IDs. This is exact parentage at save time, not a permanent path guarantee after the user renames or moves folders. [Drive folders](https://developers.google.com/workspace/drive/api/guides/folder)

Use `drive.file` rather than whole-Drive access: it permits creating new files and managing app-created or user-authorized files. It is a recommended non-sensitive scope, but OAuth consent/project configuration still applies. Existing same-named folders outside that grant cannot be assumed discoverable or writable. **Implication:** reuse app-created folders by ID; separately decide how users authorize an existing folder and how ambiguity is shown. Do not expand permissions merely to deduplicate names. [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

Android recommends `AuthorizationClient` for access to Google user data, with permissions requested when a user initiates an action. Its basic flow returns a short-lived access token; offline server access is a separate server-authorization-code flow. **Implication:** the Android client can call Drive directly with the access token and avoid requesting server offline access. Keep Google account details, access tokens, export contents, and returned provider IDs out of the Cloud EPUB backend and logs. Google itself necessarily receives the authorized upload. Provider authorization is separate from the app's username/password identity. [Google authorization on Android](https://developer.android.com/identity/authorization)

Drive's hidden `appDataFolder` is inaccessible through normal Drive UI and therefore does not satisfy the user's readable `Cloud ePub/Recovery` folder request. [Drive app data](https://developers.google.com/workspace/drive/api/guides/appdata)

## Cancellation, duplicates, replacement, and secret exposure

- Drive names are not unique within a folder. **Implication:** a name match alone cannot identify an existing recovery file or safely authorize overwrite; bind saved IDs to the selected provider account and handle moved/deleted folders and reconnects. [Drive File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)
- Drive permits pre-generated IDs for ordinary files/folders, making retries after ambiguous failures avoid duplicate creates; a repeated successful ID produces conflict rather than another file. **Implication:** record the operation's ID and reconcile its result before retrying blindly. Cancellation after an upload was accepted cannot guarantee rollback. [Drive file creation](https://developers.google.com/workspace/drive/api/guides/create-file)
- Drive can trash or permanently delete authorized files; trash and permanent deletion differ. **Implication:** replacement/deletion of a known export can be offered only within granted permissions and cannot retract copies, screenshots, another provider's backups, or files no longer accessible. Never describe deletion of one remote file as removal of every secret copy. [Drive deletion](https://developers.google.com/workspace/drive/api/guides/delete)
- **Security implication:** readable export gives the provider account and anyone able to read/download/share that file the Recovery code. Explain this before the explicit save action and require actual acknowledgement of saving the current package; do not silently upload or make the package public. Creation, consent denial, offline failure, and unsuccessful cleanup must be visible states.
- **Cryptographic implication, not a protocol claim:** invalidating an old code for online account recovery does not prove that the code becomes useless against previously copied ciphertext/key wrappers. That depends on the eventual encryption/key-rotation design. Replacing a text file cannot change existing copies. Distinguish online revocation from protection of historical snapshots and avoid promising retrospective confidentiality.

## Remaining decisions and verification evidence

Product clarification still needs explicit logout behavior, supported provider/export success wording, reconnect/duplicate policy, and whether replacement is offered or manual. The technical decision must select encryption/key rotation and review renderer storage behavior. Nothing was implemented, and no Android device/provider integration was exercised. Before calling the design build-ready, verify ordinary explorer and URI exclusion, offline local unlock after cloud expiration, crash/lock cleanup, backup and transfer exclusions across supported OS/OEMs, SAF cancellation/offline behavior, and Drive consent, parent IDs, retries, duplicate folders, lost grants, and rotation failure paths.
